# 面试讲解与追问准备

## 两分钟讲解顺序

1. 问题：用户可能用自然语言、商品图或图文组合表达购物需求，同时价格和库存必须可信。
2. 架构：Planner 只决定工具和参数；Retriever 负责候选；库存/对比由确定性工具执行；答案只引用工具证据。
3. 多模态：Chinese-CLIP 把商品文本、主图和查询图编码到 512 维共享空间，索引离线构建并绑定目录哈希和模型 ID。
4. 评测：用 ABO 其他视角作查询、主图作索引，避免原图找自己；与 RGB 直方图和词法基线对照。
5. 结果：跨视角 R@1 由 0.1667 到 0.7500；文本属性集没有全面提升，进一步验证了词法与稠密融合的必要性。
6. 工程：FastAPI、图片安全校验、JSON Schema dispatcher、Docker、CI、一键 CPU 复现和失败案例输出。

## 高频追问

### 为什么不用纯向量检索？

电商查询中品牌、型号、材质等精确 token 很重要。实验中 CLIP 文本/图文索引在属性困难集的 R@5 和 MRR 低于词法基线，因此保留词法召回，并提供可调分数融合，而不是用单一模型覆盖所有信号。

### 为什么跨视角评测更可信？

原图同时作为查询和索引时，模型可能依靠像素级近似获得 1.0，无法证明语义泛化。跨视角集从同一商品的 `other_image_id` 取查询图，索引仍用 `main_image_id`，因此更接近用户拍照搜商品。

### 为什么没有直接上 FAISS？

当前实验只有 100 个商品，NumPy 精确余弦搜索更容易验证且没有近似召回损失。接口把检索器和 Agent 解耦；扩展到十万级商品时可替换为 FAISS/HNSW，并比较延迟、内存和召回损失。

### 如何防止模型编造价格和库存？

模型或规则 planner 只能生成注册工具的名称和参数。Dispatcher 用 Pydantic Schema 拒绝额外字段、类型错误与非法工具；价格和库存由商品工具返回。最终回答携带商品 ID 引用，评测期望引用与目录有效性。

### 目前最大的局限是什么？

真实 test 集只有 12 个商品，置信区间较宽；失败集中在同品牌相似手机壳，说明细粒度图案和机型识别不足。下一步会扩大数据、按类目分层划分验证/测试，并尝试 hard-negative 重排或细粒度 VLM 属性抽取。

## 现场演示路径

1. 打开 Web 首页，先做文字预算检索；
2. 上传商品图片，展示图像检索与引用商品 ID；
3. 调用比较或库存意图，展示工具轨迹；
4. 打开 `/docs` 展示请求 Schema 和 `/tools` 注册表；
5. 展示 `docs/EXPERIMENT_LOG.md` 的正结果、负结果与失败案例，而不只展示单个成功截图。
